# 4.18 Resilience, Abuse, and Availability (`ABUS`)

[← Chapter 4 overview](README.md) · [Test case format](test-case-format.md)

## Overview

Resilience tests cover **abuse at scale**: tool-call storms, concurrency limits, retry semantics on non-idempotent operations, and cost amplification via model loops.

## Why this category matters

Agentic hosts can hammer tools and upstream APIs. Missing limits causes financial abuse, lockouts, or data corruption from duplicate writes.

## Scope

Rate limits, concurrency caps, idempotency keys, circuit breakers, planner retry policy.

## When to prioritize

High for production agents with billing-sensitive upstreams or write-heavy tools.

## Related categories

[AGNT](4.09-agentic-workflow.md), [GW](4.16-gateway-egress.md), [TRNS](4.15-transport-channel.md)

## Common test chains

ABUS-02 + AGNT-05; ABUS-01 + GW-03.

### MCPSTG-ABUS-01 — Test Tool-Call Storms and Concurrency Limits

<a id="mcpstg-abus-01"></a>

#### Summary

Agentic MCP hosts can invoke tools in **tight loops** or at **high concurrency** when a planner retries, misinterprets errors, or follows poisoned instructions. Without host-level and server-level limits, a single session can exhaust CPU, flood upstream APIs, inflate token cost, or trigger account lockouts. This test checks whether rate limits, concurrency caps, and backpressure exist **before** shared infrastructure is impacted.

#### Scenario

- **MCP host/client:** `<TEST_USER>` runs a lab agent host connected to `<AUTHORIZED_LAB_SERVER>`.
- **MCP server:** exposes `<TEST_TOOL_NAME>` that performs a cheap but measurable action (for example a read or synthetic HTTP call to a lab-only endpoint).
- **Trust boundary:** between **planner retry policy**, **host throttling**, and **server/gateway enforcement**.
- **Attacker position:** abusive automation, runaway agent loop, or prompt that encourages repeated tool use.
- **Potential impact:** availability degradation, financial abuse (API billing), upstream rate-limit bans.

#### Test Objectives

- Verify maximum **calls per minute** and **concurrent in-flight** tool calls are enforced.
- Verify the host surfaces throttling to the user/model without silent infinite retry.
- Verify logs and metrics expose storm patterns for detection.

#### Preconditions

- Authorized lab with a dedicated MCP server and synthetic tool only.
- Ability to run a bounded concurrency script (see **Example snippets**).
- Metrics or logs for tool-call count, latency, and throttle/deny events.

#### How to Test

##### 1. Manual Review

Review host and server documentation for documented rate limits, queue depth, and planner retry policies.

##### 2. Configuration Review

Inspect host MCP policy, gateway throttling, and server-side limits. Note whether limits apply per user, per server, or globally.

##### 3. Runtime Testing

1. Establish baseline latency with a single `tools/call`.
2. Run the bounded burst script below with `limit=5`, then `20`, then `50` (stop if lab policy says so).
3. Record HTTP/MCP error codes, queue times, and whether calls are dropped or delayed.

##### 4. Abuse Case Testing

Combine burst traffic with a prompt that asks the model to “keep trying until success” and observe whether the host stops the loop.

##### 5. Log and Detection Review

Confirm throttle/deny events include principal, tool name, limit name, and correlation ID.

#### Example snippets

Lab host configuration:

```json
{
  "mcpServers": {
    "<AUTHORIZED_LAB_SERVER>": {
      "command": "node",
      "args": ["<TEST_WORKSPACE>/servers/lab-server/index.js"]
    }
  }
}
```

Single tool call (baseline):

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": { "query": "baseline-lab-1" }
  }
}
```

Bounded concurrency burst (authorized lab only):

```python
import asyncio
import json

async def call_tool(send, n):
    req = {
        "jsonrpc": "2.0",
        "id": n,
        "method": "tools/call",
        "params": {
            "name": "<TEST_TOOL_NAME>",
            "arguments": {"query": f"lab-burst-{n}"},
        },
    }
    return await send(json.dumps(req))

async def burst(send, limit=20):
    return await asyncio.gather(*[call_tool(send, i) for i in range(limit)])
```

Example host policy shape:

```yaml
mcp:
  rateLimits:
    toolsCall:
      maxPerMinute: 30
      maxConcurrent: 5
  planner:
    maxRetriesPerTool: 2
```

#### Test Data / Example Payloads

Use synthetic tool arguments only. Do not aim burst scripts at production endpoints or shared lab infrastructure without explicit approval.

#### Expected Results

- **Secure:** excess calls receive `429`/policy deny or queued backpressure; planner stops after configured retries; SIEM can alert on threshold breaches.
- **Insecure:** unbounded parallel calls succeed; upstream errors cause uncontrolled retry storms; no throttle telemetry.
- **Evidence:** redacted log lines showing limit enforcement, script parameters used, before/after call counts.

#### Remediation

- Enforce **per-principal** and **per-tool** rate limits on the host and gateway.
- Cap planner retries and require exponential backoff with jitter.
- Add circuit breakers when error rates spike.
- Expose metrics: `mcp_tool_calls_total`, `mcp_tool_throttled_total`.

#### Tools

Load generators (bounded), MCP client libraries, structured log search, metrics dashboards.

- CWE-770: Allocation of Resources Without Limits or Throttling.

### MCPSTG-ABUS-02 — Test Retry Behavior for Idempotent versus Non-Idempotent Side Effects

<a id="mcpstg-abus-02"></a>

#### Summary

MCP agent hosts **retry failed tool calls** by default in many frameworks. Retrying **read-only** tools is usually safe; retrying **writes**, payments, or ticket creation without **idempotency keys** can duplicate side effects. This test verifies that retries are policy-driven, that non-idempotent tools require keys or human approval, and that duplicate requests do not double-apply changes.

#### Scenario

- **MCP host/client:** lab agent with retry enabled on transient errors.
- **MCP server:** `<TEST_TOOL_NAME>_write_marker` writes a marker file under `<TEST_WORKSPACE>/sandbox/`.
- **Trust boundary:** planner retry logic ↔ tool side-effect classification ↔ server idempotency store.
- **Attacker position:** flaky network simulation or deliberate timeout to trigger retries.
- **Potential impact:** duplicate records, double charges, corrupted workspace state.

#### Test Objectives

- Verify idempotent retries are allowed for read-only tools.
- Verify non-idempotent tools reject duplicate execution without a stable idempotency key (or dedupe correctly when the same key is replayed).
- Verify logs distinguish first attempt vs. retry vs. duplicate suppressed.

#### Preconditions

- Authorized lab with a synthetic write tool and sandbox directory.
- Ability to simulate timeout or `503` once, then success (lab harness).
- Log access showing request IDs and idempotency keys if supported.

#### How to Test

##### 1. Manual Review

Document which tools are classified as read vs. write vs. financial. Confirm retry policy per class.

##### 2. Configuration Review

Inspect host config for `maxRetries`, idempotency header/field support, and write-tool approval gates.

##### 3. Runtime Testing

1. Call the write tool once with `"idempotencyKey": "lab-run-1"` — confirm one marker file.
2. Replay the **same** JSON-RPC request — secure systems dedupe (still one marker).
3. Replay with a **new** key — should require explicit approval or be denied by policy.
4. Induce one transient failure mid-flight and observe retry behavior.

##### 4. Abuse Case Testing

Ask the model to “try again until the file exists” after a partial failure; verify the host does not create duplicate artifacts.

##### 5. Log and Detection Review

Logs should show `attempt=1/2`, idempotency key, and `deduped=true` when applicable.

#### Example snippets

Non-idempotent write (initial):

```json
{
  "jsonrpc": "2.0",
  "id": 10,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>_write_marker",
    "arguments": {
      "path": "<TEST_WORKSPACE>/sandbox/marker.txt",
      "idempotencyKey": "lab-run-1"
    }
  }
}
```

Retry replay (same key — should dedupe):

```json
{
  "jsonrpc": "2.0",
  "id": 11,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>_write_marker",
    "arguments": {
      "path": "<TEST_WORKSPACE>/sandbox/marker.txt",
      "idempotencyKey": "lab-run-1"
    }
  }
}
```

New key without approval (should deny or escalate):

```json
{
  "jsonrpc": "2.0",
  "id": 12,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>_write_marker",
    "arguments": {
      "path": "<TEST_WORKSPACE>/sandbox/marker.txt",
      "idempotencyKey": "lab-run-2"
    }
  }
}
```

Host retry policy (example):

```yaml
mcp:
  retries:
    defaultMax: 2
    idempotentMethods: ["tools/call:read_only"]
    requireIdempotencyKeyFor:
      - sideEffect: write
      - sideEffect: network_mutation
```

#### Test Data / Example Payloads

Use sandbox paths under `<TEST_WORKSPACE>` only. Marker content should be non-sensitive (`lab-marker-<timestamp>`).

#### Expected Results

- **Secure:** duplicate same-key calls are deduped; new keys on write tools require approval; retries stop at configured max.
- **Insecure:** each retry creates a new file/record; no idempotency support on write tools; unlimited retries on failures.
- **Evidence:** directory listing hash before/after, redacted logs with keys and attempt counts.

#### Remediation

- Classify tools by side-effect type; disable blind retries on mutating tools.
- Require idempotency keys end-to-end (host → server → upstream API).
- Use outbox/saga patterns for multi-step agent workflows.
- Alert when write tool call count exceeds 1 per user intent correlation ID.

#### Tools

MCP client, filesystem diff, log correlation, fault-injection proxy (lab only).
