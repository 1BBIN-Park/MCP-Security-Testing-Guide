# 4.15 Transport and Channel Security (`TRNS`)

[← Chapter 4 overview](README.md) · [Test case format](test-case-format.md)

## Overview

Transport tests examine **how MCP messages move**: TLS configuration, certificate validation, authentication binding to the channel, message size limits, and timeouts under load.

## Why this category matters

Remote MCP over HTTP introduces classic channel threats—MITM, credential theft, and DoS—on top of tool-level risks.

## Scope

TLS versions/ciphers, cert pinning, mTLS, session binding, max payload sizes, idle and read timeouts.

## When to prioritize

Mandatory for **remote** MCP; lower for pure stdio local-only deployments.

## Related categories

[AUTHN](4.03-identity-authentication.md), [GW](4.16-gateway-egress.md), [ABUS](4.18-resilience-abuse.md)

## Common test chains

TRNS-01 + AUTHN-02; TRNS-03 + ABUS-01 (storms/timeouts).

### MCPSTG-TRNS-01 — Test TLS Configuration and Certificate Validation

<a id="mcpstg-trns-01"></a>

#### Summary

Remote MCP transports rely on TLS for confidentiality and integrity between **client** and **server**. Weak cipher suites, missing certificate validation, or mis-terminated TLS at an untrusted hop exposes tokens, tool arguments, and resource payloads. MCP deployments often sit behind reverse proxies; misconfiguration there becomes part of the MCP trust boundary.

#### Scenario

- **MCP host/client:** Connects to a remote MCP endpoint over HTTPS.
- **Infrastructure:** TLS terminates at a load balancer; backend may be plaintext on a private network.
- **Attacker position:** Network observer on untrusted Wi‑Fi path to public endpoint; or compromised proxy in a misconfigured enterprise path.
- **Potential impact:** Credential theft, session hijack, undetected tampering with tool definitions in transit.

#### Test Objectives

- Verify **TLS versions**, **cipher strength**, and **certificate chain validation** meet organizational baselines.
- Verify **SNI** and **hostname** validation align with the MCP server identity.
- Identify **insecure** patterns: cert pinning disabled globally, `insecureSkipVerify`-style flags, mixed content downgrades.

#### Preconditions

- Authorized test against **lab** MCP HTTPS endpoint (not customer production).
- Permission to run TLS assessment tooling from an approved scanner host.
- Access to proxy/load balancer configuration (redacted).

#### How to Test

##### 1. Manual Review

Read deployment docs for TLS termination points and which component validates client certificates (if mTLS is claimed).

##### 2. Configuration Review

Inspect server and proxy configs for deprecated protocols (TLS 1.0/1.1), weak DH parameters, and permissive trust stores shipping private roots without justification.

##### 3. Runtime Testing

1. Connect with a known-good client and capture negotiated TLS version/cipher via approved SSL scanning (lab scope).
2. Attempt **hostname mismatch** using a valid certificate for a different name—expect **failure**.
3. If mTLS is required, attempt connection **without** client cert—expect **failure**.

##### 4. Abuse Case Testing

- Certificate expiry near-miss: deploy short-lived lab cert and verify renewal alarms (process test).
- Revocation behavior: document whether stapled OCSP/CRL checks are enforced (design documentation acceptable if live revocation tests are disallowed).

##### 5. Log and Detection Review

**Detection:** TLS handshake failures, cert validation errors, and proxy anomalies should be logged with client identity where available.

#### Test Data / Example Payloads

Use scanner profiles restricted to `<AUTHORIZED_LAB_SERVER>` hostnames only.

#### Expected Results

- **Secure:** TLS 1.2+ with modern ciphers; strict hostname validation; no silent bypass flags in production paths.
- **Insecure:** handshake succeeds with obsolete ciphers; tool traffic readable on the wire in lab capture.
- **Evidence:** redacted scan summary, config snippets with secrets removed.

#### Remediation

- Enforce TLS 1.2+ and modern cipher suites at the edge; automate cert lifecycle.
- Avoid `insecureSkipVerify` in production builds; isolate debug builds.
- Document trust store ownership and change control.

#### Tools

- Approved TLS scanners, `openssl s_client` in lab, cloud provider TLS policy dashboards.

#### References

- OWASP Web Security Testing Guide (structure inspiration only).
- OWASP ASVS: V9 Communications (TLS-related verification).
- CWE-295: Improper Certificate Validation
- CWE-326: Inadequate Encryption Strength

#### Mapping

- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/): [V13.2](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x23-V13-API-web-services.md) (TLS configuration and certificate validation)

- Risk level: High
- Testing type: Hybrid

### MCPSTG-TRNS-02 — Test Transport Authentication Binding

<a id="mcpstg-trns-02"></a>

#### Summary

**Transport authentication binding** asks whether MCP sessions are tied to the **intended identity, tenant, and origin** for the transport in use. Failures include accepting bearer tokens on the wrong virtual host, missing **origin** checks on browser-originated traffic, confused deputy behavior behind shared reverse proxies, and stdio servers that treat **any local process** on the pipe as trusted.

#### Scenario

- **Remote transport:** MCP over HTTPS where the same load balancer serves multiple tenants or environments.
- **Local transport:** stdio MCP server launched by a host; a second local process attempts to attach if file descriptors leak or sockets are world-accessible (misconfiguration).
- **Attacker position:** Network client presenting a stolen token to the wrong MCP base URL; or local malware exploiting permissive IPC.
- **Potential impact:** Cross-tenant tool execution, session fixation, or silent proxy mis-routing of MCP JSON-RPC.

#### Test Objectives

- Verify tokens and session handles are **audience-bound** (hostname, path prefix, tenant id) where applicable.
- Verify browser-facing deployments use appropriate **origin**, **CORS**, and **cookie** flags consistent with your threat model—not “wide open because it is internal.”
- Verify stdio/socket transports cannot be reached from unintended OS principals.

#### Preconditions

- Lab URLs for at least two logical MCP “tenants” or path prefixes on the same infrastructure (if that matches production topology).
- Two test tokens (or mTLS identities) scoped to different audiences, synthetic only.
- Permission to inspect proxy routing rules (redacted).

#### How to Test

##### 1. Manual Review

Document the chain: **who authenticates whom** (client→server, server→upstream). Identify whether the MCP endpoint URL is part of the cryptographic or logical binding for tokens.

##### 2. Configuration Review

- For HTTPS: check virtual host routing, default backends, and whether a missing `Host` header falls through to a sensitive MCP instance.
- For cookies (if used): `Secure`, `HttpOnly`, `SameSite`, path scope.
- For stdio: process launch arguments, file descriptor inheritance, and socket filesystem permissions.

##### 3. Runtime Testing

1. Obtain a **valid** lab token scoped to tenant A.
2. Present it to the MCP endpoint that should only serve tenant B (same LB, different path or host)—expect **reject**.
3. Repeat with correct endpoint—expect **accept**.

##### 4. Abuse Case Testing

- Replay captured MCP messages with a rotated nonce or session id if your stack uses such fields—expect strict failure modes, not partial execution.
- If applicable, attempt cross-origin browser calls from an unauthorized lab origin—expect deny.

##### 5. Log and Detection Review

**Detection:** authentication failures should log **reason codes** (audience mismatch, unknown client, clock skew) without printing secrets.

#### Test Data / Example Payloads

Use synthetic hostnames only, for example `mcp-lab-a.<AUTHORIZED_LAB_SERVER>` vs `mcp-lab-b.<AUTHORIZED_LAB_SERVER>`.

#### Expected Results

- **Secure:** wrong audience or origin cannot initialize a session or call tools; stdio server only parent process can communicate.
- **Insecure:** token works on unintended tenant route; world-readable Unix socket accepts connections.
- **Evidence:** redacted proxy rules, auth error logs, minimal PCAP excerpts in lab.

#### Remediation

- Bind access tokens to **issuer, audience, and MCP resource identifier**; reject default-backend fallthrough.
- Harden local transports: least-privilege OS users, restricted socket paths, explicit parent–child process relationship checks where feasible.
- Prefer mTLS or signed connection bootstrap for high-risk remote MCP.

#### Tools

TLS proxies, JWT debugging utilities (lab tokens only), web browser devtools for origin checks, `lsof` / permission audits for local sockets.

#### References

- OWASP ASVS: V2 Authentication, V3 Session Management, V9 Communications.
- OWASP API Security Top 10: API2 Authentication Failures.
- CWE-287: Improper Authentication
- CWE-306: Missing Authentication for Critical Function

### MCPSTG-TRNS-03 — Test Message Size Limits and Timeouts Under Load

<a id="mcpstg-trns-03"></a>

#### Summary

MCP sessions can carry **large tool results**, **big resource reads**, or **verbose logging** embedded in JSON-RPC payloads. Without **maximum message size**, **stream backpressure**, and **timeouts**, servers become fragile under abuse or accidental “runaway” model outputs. This is availability and sometimes confidentiality (crash-induced error pages, partial writes).

#### Scenario

- **Host + model** return a multi-megabyte tool payload (logs, file dumps) in a single response.
- **Attacker or buggy tool** sends an oversized argument blob or floods parallel `tools/call` requests.
- **Potential impact:** process OOM, thread pool exhaustion, cascading failures in shared gateways, inflated egress costs.

#### Test Objectives

- Verify hard and soft limits on **request and response** sizes at client, server, and gateway.
- Verify **timeouts** for idle streams, slow clients, and hung tool executions.
- Verify **graceful** rejection (typed error) rather than opaque crashes.

#### Preconditions

- Lab-only load driver permitted in scope (low concurrency first).
- Monitoring for CPU, memory, and open connections on MCP server and gateway.

#### How to Test

##### 1. Manual Review

Read limits documentation: defaults, overrides, and whether limits differ for stdio vs HTTP.

##### 2. Configuration Review

Inspect gateway `max_body_size`, server read buffers, client timeouts, and tool-specific caps (for example “max bytes read from file tool”).

##### 3. Runtime Testing

1. Send a **just-below-limit** synthetic payload and confirm success.
2. Send a **just-above-limit** payload—expect HTTP 413 or protocol-specific error without server crash.
3. Open a connection and **stall** sending mid-message beyond idle timeout—expect disconnect and cleanup.

##### 4. Abuse Case Testing

- Bounded parallel tool calls (N small calls), stepping N upward until latency budgets break—stop before harming shared infrastructure.
- Very long-lived SSE/WebSocket streams: verify heartbeat and max duration.

##### 5. Log and Detection Review

**Detection:** rate-limit hits, timeout reasons, and payload size rejections should appear in metrics with MCP method names.

#### Test Data / Example Payloads

Generate in-lab random base64 blobs of known sizes (for example 512 KiB, 2 MiB, 8 MiB) **without** compressing secrets into them.

#### Expected Results

- **Secure:** limits enforced with clear errors; no sustained memory growth; connections closed cleanly.
- **Insecure:** worker crash, gateway 502s to unrelated tenants, or silent truncation that corrupts JSON framing.
- **Evidence:** metric charts, redacted error payloads, versioned config snippets.

#### Remediation

- Enforce layered limits: edge, MCP server, tool runtime.
- Stream large artifacts to object storage with signed URLs instead of inline MCP messages where appropriate.
- Add circuit breakers and per-principal concurrency caps (`MCPSTG-ABUS-01`).

#### Tools

Load generators in lab, observability stacks, `curl`/`h2load` with size-controlled bodies where permitted.
